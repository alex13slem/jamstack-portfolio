# Аудит портфолио и направления развития

Дата: 7 ноября 2026 года. Проверен текущий локальный проект `jamstack-portfolio`.

Главный вывод: портфолио показывает умение собирать сайты с интерактивностью, но слабо объясняет ценность работ и недостаточно демонстрирует разработку приложений с данными, правами и сложными состояниями. Усиление кейсов и исправление взаимодействий дадут больше пользы, чем новые декоративные эффекты.

Ориентир рекомендаций: заказы на бизнес-сайты и веб-приложения, позиции full-stack TypeScript developer. Для узкой frontend-позиции акценты стоит сместить к интерфейсам и доступности.

## Что проверено

- Прочитан код общих компонентов, главной страницы, страниц проектов, локализации, контентных коллекций, CMS и стилей.
- `npm run build` — успешно; созданы статические страницы обеих локалей и четыре страницы проектов в каждой локали.
- `node_modules/.bin/tsc --noEmit` — успешно. Это не проверка шаблонов `.astro` и `.svelte`; отдельные проверяющие инструменты для них не установлены.
- Реальный браузер: собранная версия через локальный preview; английская и русская главные, Stakandon, переход EN → RU.
- Просмотрены размеры 1280 × 720, 390 × 844 и 320 × 740. На просмотренных главных страницах горизонтального переполнения документа не обнаружено.
- Проверены доступные названия ссылок, DOM, расположение заголовков и метаданные собранного HTML.
- Код сайта не изменялся. Этот документ — результат аудита.

Ограничения: Lighthouse, axe, полная проверка клавиатурой и скринридером, реальные Core Web Vitals, production-хостинг, внешние сайты и вход в CMS не проверялись. Режим без JavaScript и отключённый WebGL отдельно в браузере не включались: соответствующие выводы ниже следуют из реализации. Dev-сервер показал ошибку доступа при обработке зависимостей; визуальная проверка выполнена на успешно собранном preview. Эта ошибка не считается дефектом production-сайта.

## Что уже стоит сохранить

- Astro со статической генерацией, содержимое в Markdown, схемы коллекций и две локали — хорошая основа.
- Есть коммерчески понятные работы: благотворительный фонд, 3D-конструктор стаканчиков, CMS и CRM-интеграции.
- Source Sans 3 обеспечивает читаемый основной текст; рукописный логотип и персонаж могут стать личным узнаваемым элементом.
- Контакт доступен из шапки; есть ссылки на GitHub и LinkedIn.
- На основных страницах есть `lang`, description и один основной `h1`.

## Дизайн: рекомендуемое направление

Визуальная оценка: тёмная основа, сетка и личный персонаж могут работать вместе. Сейчас одновременно конкурируют большой градиентный заголовок, цветовые пятна, вращающиеся обводки, искажения картинок, лента и пословное появление текста. У всех кейсов одинаковая карточка и сходная иерархия. Eisvil в спокойном состоянии представлен фэнтезийной картинкой, а не интерфейсом: это плохо объясняет выполненную работу.

Предлагаемый характер — персональная инженерная мастерская с демонстрацией конкретных решений. Запоминающийся элемент — один интерактивный разбор реальной работы, например настройка стаканчика с видимой передачей заявки в процесс. Его окружение спокойное. Персонажа можно оставить как небольшую подпись автора; на ширине 320 px сейчас он визуально заходит под основную кнопку.

Это направление для следующего этапа, не готовый редизайн. Предварительная система:

- Цвета: фон `#090F16`, поверхность `#182129`, основной текст `#F4F7FA`, вторичный `#B9C6D2`, интерактивный голубой `#77D8EA`, подтверждённый результат `#9DE0BC`. Контраст проверить на итоговых сочетаниях.
- Шрифт: сохранить Source Sans 3 для интерфейса и текста; Shadows Into Light использовать только в подписи/логотипе. Масштаб 16/20/28/40/56 px с адаптивными пределами и строкой текста примерно до 65–75 знаков.
- Выравнивание: основные заголовки, описания кейсов и длинный текст слева; центрирование только у короткого завершающего приглашения.
- Структура: краткое позиционирование → два сильнейших кейса → остальные работы → способ работы и личный вклад → прямой контакт.
- Движение: одна необязательная интерактивная демонстрация, запускаемая пользователем. Статические картинки и текст должны полностью выполнять задачу без эффектов.

```text
Имя                  Работы   Обо мне   EN/RU   Написать

Конкретная специализация      Главный кейс / реальный интерфейс
Кому и какую задачу решаю     Задача → решение → результат
[Посмотреть работы] [Написать]

Избранные работы
Кейс: контекст, мой вклад, результат, скриншот, подробности
Кейс: контекст, мой вклад, результат, скриншот, подробности

Как работаю / что беру на себя
Прямой контакт
```

Проверка на шаблонность: первая идея просто уменьшить градиенты оставила бы универсальный набор карточек разработчика. Поэтому главный визуальный акцент предлагается перенести на специфическую демонстрацию уже выполненного проекта. Новые цвета и шрифты сами по себе уникальности не создадут.

## Как усилить существующие кейсы

Каждый кейс должен отвечать на шесть вопросов: кому нужен продукт, какая была задача, что сделал лично автор, какие были ограничения, почему выбрано решение, чем подтверждается результат.

- Stakandon: показать конструктор, путь заявки в AmoCRM и компромиссы при реализации 3D. Два месяца MVP уже указаны; не придумывать рост продаж.
- Благодействие: сделать срок 2,5 недели и запуск к конференции центральной историей; показать сайт и последующее расширение. Отзыв публиковать только с разрешения.
- Eisvil: заменить абстрактную обложку демонстрацией сайта/CMS, показать сценарий редактора и доставку обращения из формы.
- Само портфолио: краткий технический кейс с измерениями до/после оптимизации. Убрать повторяющийся каталог библиотек и неподтверждённые заявления.

## Какие пет-проекты добавить

Лучший пробел для заполнения — полноценное бизнес-приложение. Ещё один лендинг, CMS-сайт или 3D-конструктор в значительной мере повторит имеющиеся доказательства. Приоритеты ниже — оценка соответствия этому портфолио, а не статистика спроса на вакансии.

### 1. Кабинет заказчика для небольшой дизайн-студии — первый выбор

**Задача:** согласовать заказ и материалы, видеть сроки, обсуждать правки и сдавать результат без потери информации в переписке.

**Ограниченный первый выпуск:** роли заказчика и менеджера; заявка; смета; согласование; статусы выполнения; файлы с версиями; комментарии; история изменений. Один тип заказа и один сквозной процесс. Уведомления — через один канал. Биллинг, календарь, чат в реальном времени и сложную аналитику отложить.

**Что доказывает заказчику:** можно организовать его рабочий процесс и клиентский сервис. **Что доказывает работодателю:** модель данных, серверная авторизация, переходы статусов, работа с файлами, транзакции и обработка конфликтов.

**Сильная демонстрация:** клиент согласует версию сметы, менеджер запускает работу, клиент видит тот же заказ из своего кабинета. Попытка открыть чужой заказ получает отказ на сервере. Начать с одной студии; изоляцию нескольких организаций добавлять отдельным этапом, если это нужно выбранным вакансиям.

**Технологическое направление:** TypeScript, один UI-фреймворк, PostgreSQL, серверные проверки доступа и объектное хранилище. Выбирать конкретный framework по целевым вакансиям; не сочетать React и Svelte только ради списка технологий.

### 2. Сервис обработки заявок и контроля интеграций — второй выбор

**Задача:** обращения с форм попадают в CRM и уведомления, а сбои видны и исправимы. Существующий кейс Stakandon уже показывает CRM-интеграцию; здесь ценность именно в её надёжности и наблюдаемости.

**Первый выпуск:** один источник, один приёмник; проверка подписи webhook; запись события; очередь обработки; защита от повторов; повторные попытки; список ошибок и ручное повторение с проверкой прав. Симулятор CRM позволяет показать сценарий без платных ключей.

**Сильная демонстрация:** входящее событие приходит трижды, приёмник временно недоступен, затем восстанавливается — создаётся ровно одна заявка, история попыток видна. Экран полезнее заполнять реальными состояниями обработки, чем декоративными графиками.

Заказчику понятна потеря заявок; работодателю видны асинхронная обработка, идемпотентность и эксплуатация. Эти проблемы реальны: Stripe прямо предупреждает о повторах и отсутствии гарантии порядка событий в [документации webhook](https://docs.stripe.com/webhooks).

### 3. AI-поиск по базе знаний с проверяемыми ответами — третий выбор

**Задача:** сотрудники находят ответы в инструкциях небольшой сервисной компании и открывают источник ответа.

**Первый выпуск:** загрузка подготовленных документов, поиск, ответ со ссылками на конкретные фрагменты, явное «ответ не найден», обновление индекса и обратная связь. Сначала одна предметная область и один набор прав; публичная демонстрация работает только на синтетических открытых документах.

**Что делает кейс убедительным:** фиксированный набор вопросов с ожидаемыми источниками; отдельные примеры отсутствующего ответа; отчёт о корректности источников, времени и стоимости запроса. Показывать измеренные результаты и размер выборки. Для поиска по закрытым документам права должны применяться до передачи фрагментов модели.

**Сильная демонстрация:** ответ с проверяемой цитатой; вопрос, которого нет в базе; обновление документа; документ, недоступный текущей роли. Автоматическую отправку писем и изменение бизнес-данных в первый выпуск не включать.

### Вариант замены при фокусе на frontend

Вместо второго backend-проекта можно сделать планировщик ресурсов маленькой студии: доступный календарь, загрузка исполнителей и конфликты бронирований. Ценность — сложное, но понятное взаимодействие, клавиатурное управление и корректное поведение при одновременных изменениях. Не дублировать ещё один общий канбан без предметной задачи.

### Как представить каждый новый проект

- Живая демоверсия с понятным входом по ролям, синтетическими данными и восстановлением начального состояния.
- Один демонстрационный сценарий, который посетитель проходит за несколько минут; короткое видео как запасной путь.
- Кейс: проблема → ограничения → решение → подтверждённый результат → компромиссы.
- Читаемый репозиторий: быстрый запуск, схема данных, краткая архитектура и объяснение двух-трёх важных решений.
- Проверки критического поведения: доступ к чужим данным, повтор события, сбой интеграции или отсутствие ответа — по предмету проекта.
- Показать loading, empty, error и success states, мобильное поведение и работу клавиатурой.
- Для работодателя дать путь к коду и решениям; для заказчика первым показывать рабочий процесс и пользу.

Практическая последовательность: сначала исправить P1 и переписать два сильных существующих кейса, затем закончить один кабинет заказчика. После этого выбирать второй проект по реакции целевой аудитории. Три незавершённых приложения одновременно ослабят подачу.

## Порядок улучшения сайта и критерии готовности

1. **Базовая надёжность.** Убрать вложенные элементы управления, дать имена ссылкам, сделать видимый фокус и запасные изображения, исправить метаданные. Готово, когда ключевые переходы понятны и работают клавиатурой, а обложки доступны без эффектов.
2. **Содержание и навигация.** Конкретное позиционирование, явный переход к работам, актуальные контакты и переключатель языка. Готово, когда новый посетитель может быстро понять специализацию, открыть доказательство и связаться.
3. **Кейсы и мобильный порядок.** Явный порядок работ, реальные интерфейсы, личный вклад, ограничения и результаты. Готово, когда страницу проекта можно понять без расшифровки иконок и длинного перечня библиотек.
4. **Визуальное упрощение и скорость.** Один выразительный акцент, ограниченная анимация, адаптивные картинки, сокращение клиентского JS. Проверить reduced motion и измерить production Lighthouse/Core Web Vitals; не обещать оценки заранее.
5. **Новый пет-проект.** Один завершённый кабинет с демонстрационным сценарием, кодом и разбором решений. Затем — интеграции или AI-поиск по выбранному направлению.
